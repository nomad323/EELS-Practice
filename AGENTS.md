# Programming — Project Rules

- Inspect the actual language/runtime, source layout, entry points, dependencies, interfaces, and tests before choosing conventions or changing behaviour. Do not assume a framework, vendor SDK, or install command.
- Make small reviewable changes against explicit requirements, with regression tests and reversible rollout. Preserve human work. Distinguish proposed code, implemented code, checks actually run, offline validation, and deployed/hardware acceptance.
- Keep software records in `README.md`, `docs/requirements.md`, and `docs/validation.md`; add `docs/decisions/` only for substantive decisions. Use existing source/test conventions; the empty `src/` and `tests/` are starting points, not a working program.
- Ordinary coding progress does not require scientific `PROJECT.md`, `research_logs/`, a paper ledger, or scientific memory writers. If actual scientific findings arise, agree an explicit scientific provenance/logging workflow instead of relabelling them as software test results. Use user-chosen `PLAN.md` only through `research-plan` for execution checkpoints.
- For instrument-facing software, preserve known-working source, configuration/calibration baselines, and rollback paths. Begin with offline inspection and mocks, replay data, or simulation; distinguish unit/algorithm tests, offline regression validation, and operator-supervised hardware acceptance. Never infer a vendor API, control limit, or safe calibration value.
- No automatic instrument connection, live acquisition, actuator/corrector changes, calibration replacement, deployment, or disabling of interlocks. These require a separately reviewed procedure and explicit owner/operator approval. Instructions are not a hardware sandbox or evidence of validated safety.
- Report actual changed paths, tests and their results, untested behaviour, and failures. Do not fabricate successful tests or perform dependency installs, source imports, commits, or live-system work without the appropriate approval.
